## 1. BUG-01（严重，**已修复**）：首次启动未授权麦克风时，语音功能永久停用，授权后也不恢复，必须重启

### 现象

首次安装后第一次打开 App，底部"按住说话"按钮显示 **"没有可用的麦克风"**。
在弹出的权限框里允许麦克风后，**按钮状态不变、语音仍然不可用**；退出应用重进才恢复正常。

### 复现步骤

1. 清除应用数据或首次安装（`RECORD_AUDIO` 未授予）
2. 启动 App，观察底部按钮 → 显示"没有可用的麦克风"
3. 授予麦克风权限（弹窗允许，或到系统设置里手动开启）
4. 回到 App，按住"按住说话"喊"安迪" → 无任何反应，按钮文案不变
5. 杀掉进程重开 → 日志出现"离线关键词识别已就绪"，语音正常

### 日志证据

首次启动（PID 17871），**只在初始化时打了一条，之后再无任何语音相关日志**：

```text
10-30 10:13:33.401 W/Unity (17871): [VoiceKeywordListener] 没有可用的麦克风（语音功能停用，其他功能不受影响）
```

重启后（PID 11977），同一个 App 正常：

```text
10-30 10:15:34.060 I/Unity (11977): [VoiceKeywordListener] 离线关键词识别已就绪，麦克风：Android audio input
```

授权后的权限状态已确认是 granted：

```text
android.permission.RECORD_AUDIO: granted=true
```

### 根因（代码路径，行号以 2026-10-30 工作区为准）

1. `Platform/VoiceKeywordListener.cs:68` —— `Start()` 只跑一次 `Initialise()`。
2. `:72-76` —— `Microphone.devices` 为空（Android 未授予 `RECORD_AUDIO` 时 Unity 返回空数组）
   就 `SetUnavailable("没有可用的麦克风")` 然后 `yield break`，初始化**到此终止**。
3. `:304-309` —— `SetUnavailable` 把 `State` 置为 `VoiceListenState.Unavailable`。
4. `:113` —— `BeginListening()` 第一行就是
   `if (State == Unavailable || State == Listening) return;`
   **于是"未授权 → 请求权限"这条分支（`:115-118`）永远走不到**，按按钮连权限弹窗都不会弹。
5. `:328-333` —— 授权回调只把 `State` 改回 `Idle`、改文案，**不重建 `_device`、不重跑 `Initialise()`**。
   即使回调被触发，识别器依然不存在。

### 影响

- **新装用户的语音功能第一次必定失效**，且只能靠重启恢复。课堂演示如果现场第一次装包，
  会直接踩到；演示流程里没有"重启一次"这一步。
- 文档与实现不符：`AGENTS.md`、`Docs/项目使用与调试说明.md` 第 9 节、`Docs/使用说明与演示脚本.md`
  都写"首次按住按钮时请求麦克风权限"，实际这条路径不可达。
- 代码审查报告里的 P3-5（"权限授予后仍需松手重按"）低估了问题：重按也没用，`State` 已经锁死在 `Unavailable`。

### 记录备注（不作为修复方案，仅供决策）

可选方向有三个：初始化前先请求权限再判断设备；`SetUnavailable` 区分"权限缺失"与"真的没有设备"；
授权回调里重跑一次 `Initialise()`。**本轮不实施。**

## 2. BUG-02（严重，**已修复待实测**）：奶蛙上半身点不到，只有下半身和卡面能触发

### 现象

同一只奶蛙，点下半身或脚下的卡面 → 正常触发反应动作；点上半身（肚子以上、头部）
→ 完全没反应，日志里也没有交互记录。

### 证据

`02_Main` 场景里四只宠物的命中组件全部是空碰撞体 + 0.08m 半径：

```text
petId: pet_classic   hitCollider: {fileID: 0}   hitRadiusMeters: 0.08
petId: pet_calm      hitCollider: {fileID: 0}   hitRadiusMeters: 0.08
petId: pet_divine    hitCollider: {fileID: 0}   hitRadiusMeters: 0.08
petId: pet_rage      hitCollider: {fileID: 0}   hitRadiusMeters: 0.08
```

整个 `02_Main.unity` 里 **Collider 组件数量 = 0**（`!u!64/65/135/136` 一个都没有）。

### 根因（代码路径）

1. `App/TouchInputBridge.cs:263-283` —— 有碰撞体时走 `Collider.Raycast`；**碰撞体为空时**走近似：
   ```csharp
   var toCenter = target.transform.position - ray.origin;
   var projection = Vector3.Dot(toCenter, ray.direction);
   var closestPoint = ray.origin + ray.direction * projection;
   if (Vector3.Distance(closestPoint, target.transform.position) > target.HitRadius) continue;
   ```
   也就是"射线到**某一个点**的最近距离 < 0.08m"。
2. 这个点就是 `PetHitTarget` 所在物体的 `transform.position` —— `PetHitTarget` 挂在
   `PetRoot_pet_*` 上，而 `PetRoot` 位于卡面原点、也就是角色的**脚底**。
3. 于是可点区域是一个**以脚底为球心、半径 8cm 的球**。角色高 0.200m，
   这个球只覆盖脚底往上 8cm（约下半身 40%），**肚子以上全部在球外**。
4. 卡面与球心几乎重合（同一平面），所以点卡也会触发 —— 与观察完全一致。

### 影响

- "点奶蛙"是这个 App 最基本的操作，现在有一半以上区域无效；用户会认为"没反应/卡了"。
- 四宠同屏时更明显：两只宠物间距 18cm 触发共同大笑，而各自的可点球半径只有 8cm，
  中间大片区域点不到，且两球可能互相干扰。
- 这不是接线写错，而是**从来没给宠物做过碰撞体**：`Scripts/Editor/` 下的接线工具
  （菜单 5/6）只写 `PetHitTarget` 的 `petId` 与半径，没有任何 `AddComponent<Collider>`；
  `PetHitTarget.cs:22` 的 Tooltip 也明确写着"留空时按球形近似判定"。
- 附带影响：`PetPresenter` 的"关闭碰撞体"在无碰撞体时是空操作；交互禁用实际靠
  `AppRoot.cs:256` 的 `_session.CanInteractThisFrame(petId)` 逐帧过滤，功能上仍然正确。

### 记录备注（不作为修复方案，仅供决策）

可选方向：给每只宠物挂一个贴合身体的 `CapsuleCollider`（高约 0.2m、半径约 0.05～0.06m）并填进
`hitCollider`，由接线工具统一生成；或把近似判定从"脚底球"改成"以角色中心为球心的胶囊"。
**本轮不实施。**

## 3. BUG-03（中，**已修复并验证**）：存档主路径在 Android 上必然失败，每 5 秒抛一次异常

### 现象

`logcat` 里每 5 秒稳定出现一条 SELinux 拒绝，从 10:14 持续到 11:00 未间断：

```text
W UnityMain: avc: denied { link } for name="zqxnxs_save_v2.json" dev="fuse"
             scontext=u:r:untrusted_app:s0 tclass=file permissive=0 app=com.DefaultCompany.ARPet
```

### 根因

`Persistence/SaveService.cs:206` 用 `File.Replace(tempPath, path, backup)` 做主档替换。
Android 的外部存储走 FUSE，`File.Replace` 内部的 `link()` 被 SELinux 拒绝 → 抛 `IOException`
→ 落到 `:208-217` 的兜底（`CopyDurably` → `Delete` → `Move`）→ 存档仍然写成功。

所以：**功能没坏，但每次存档都要走一次异常路径**。5 秒节流一次，意味着正常游玩时
每小时约 720 次异常 + 720 条 audit 拒绝。

### 影响

1. 原子替换的保证实际从未生效，真正落地的是"先复制备份→删主档→移动"的非原子兜底。
   进程若在 Delete 与 Move 之间被杀，主档会短暂缺失（`.bak` 仍在，可恢复）。
2. audit 拒绝每 5 秒刷屏，**把 Unity 的 Debug.Log 快速挤出环形缓冲**——本轮 20 分钟后
   已经无法从 `logcat -d` 里取到任何业务日志，直接妨碍排障。

**本轮不实施修复。** 记录备注：可在 Android 上跳过 `File.Replace` 直接走兜底路径。

## 4. BUG-04（严重，**已修复并验证**）：按演示脚本"两卡并排 15cm"摆卡，共同大笑永远不触发

### 现象

两卡并排约 15cm、朝向一致、平放同一桌面，手机对准保持 10 秒以上，两只都不笑。
证据：`logcat` 全缓冲 **零条 `[SocialCoordinator]`**（既无开始也无取消）；存档四只
`SocialWatchedCount` 全为 **0**；面板停在正常 Idle，无 "Laughing together!"。

### 根因（代码路径）

`Interaction/ProximityRule.cs:316-320` 的"启动先上锁"：

```csharp
if (!state.Initialised)
{
    state.Initialised = true;
    if (measure.InEnterZone || measure.InHysteresis) state.Locked = true;
}
```

`Initialised` 指的是**这一对第一次出现"两只都可用"的那一帧**，而"可用"要求两卡**同时**
Tracked（`App/PetSession.cs:280-282`，`Usable = trackingRunning && slot.CanInteract && IsSettleable(...)`）。

真实摆卡顺序必然是：先放暖黄 → 暖黄已 Tracked；再放湖蓝 → 湖蓝进入 TRACKED 的**那一帧**，
两卡已经相距 15cm，落在进入区（`EnterDistance = 0.18`）→ 立刻 `Locked = true`。
从此无论停多久都不会开演。

更宽的范围：`InHysteresis` 也上锁，即 **18～23cm 的迟滞带，或高差 >3.5cm，或夹角 >20°，
只要第一次"两卡同时可见"时距离 < 23cm，这一对就锁死**。

解锁条件（`ProximityRule.cs:329-339`）：两卡**同时 Tracked** 且相距 ≥ `ExitDistance = 0.23m`，
保持 `ExitDwellSeconds = 0.3s`。注意"丢失不等于离开"——把卡拿出画面不算分开，`Separated` 会被清零。

### 这不是写错，是设计

`ProximityRuleTests.cs:246 StartupAlreadyTouching_LocksUntilSeparatedAndReapproached` 第一帧
就用 `Close(0.15f)` 并断言 `IsLocked == true`。所以 **255/255 全过与"真机笑不出来"不矛盾**：
测试验的是设计，而这个设计与演示脚本互相冲突。

设计意图是"打开应用时已经贴在一起不该凭空开演"，但它同时把**最常见的自然操作**——
"摆好一张，再把第二张放到它旁边"——判定成了"启动即贴住"。

### 与文档的冲突

- `Docs/使用说明与演示脚本.md:16`：「把两张卡并排放（间距约 15cm 以内、朝向大致一致、平放在同一桌面），停一会儿」→「两只同时大笑」
- 同文件 `:32` 分镜：「1:50 放上湖蓝卡，两卡并排」→「两只同帧大笑」

按这个脚本在**全新会话**里操作，必然不触发。

### 影响

1. 核心玩法第二条（共同大笑）在标准演示流程下**不可达**，现场演示必然卡住。
2. 唯一可行路径是"两卡先拉开 ≥23cm 且同时入镜 → 保持 0.3s → 再并到 15cm"，文档里没有这一步，
   用户无法自行发现。
3. 三只以上同屏时同样受此规则约束：任意一对第一次同时可见时若已贴近，该对永久锁死到分开为止。
4. **竖屏形态下连"绕行路径"也走不通**：解锁要求两卡同时入镜且相距 ≥0.23m，竖屏横向视野装不下，
   详见 O-9。即当前构建里共同大笑实质不可达。

### 记录备注（不作为修复方案，仅供决策）

可选方向：① 给"启动上锁"加更严的触发条件（例如只对本次会话的第一次接近生效，或要求上锁帧两卡
都在视野中央）；② 放宽为"上锁但允许一次合格停留后自动解锁"；③ 仅改文档，把演示脚本改成
"先分开再靠近"。**本轮不实施修复。**

## 5. BUG-05（中，**15:36 构建已修复，待实测**）：专属演出期间点按或喊口令被拒，会把招牌表情打回原样，动作却继续播

### 现象

红（rage）、紫（divine）奶蛙满值专属演出时，眼睛先变成招牌表情（怒眼 / 纯白发光眼），
但在动作**还没播完**时眼睛就回到原来的颜色，动作本身仍继续播到结束。
classic / calm 同样会发生，只是它们的招牌表情是"眯眼 / 闭眼"，回落不如红紫扎眼。

### 根因（代码路径，全部可核对）

1. `Pet/BehaviorStateMachine.cs:99`：`IsBusy => _behaviorActive && CurrentIsOneShot`。专属是一次性行为，
   演出期间 `IsBusy` 恒为 `true`。
2. 演出期间的**任何**一次点按或语音口令都走 `TryAcceptPet():376` / `TryAcceptVoice():205`
   的 `if (IsBusy) return Refuse();`。
3. `Refuse():461-466` 无条件执行 `_presenter.SetExpression(PetExpression.Refuse, 1f)`。
4. `Presentation/FaceExpressionTable.cs:74`：`PetExpression.Refuse => new Cells(null, Flat)` —— **eyes 为 `null`**。
   `PetPresenter.ApplyCell` 于是关掉眼睛贴片、`ApplyBodyCover` 恢复原材质 → 眼睛回到原色。
5. 行为本身没被打断（`CompleteCurrent` 未被调用），动画继续播到 `DurationSeconds`。

即：**"拒绝一次输入"错误地改写了画面**。Refuse 的语义只是"这次输入没被接受"，不应该动表情。

### 为什么红/紫最明显

`FaceExpressionTable.cs:63-69`：`Signature` 对 rage 是 `怒眼 + 怒吼`、divine 是 `纯白发光眼 + 舒展`；
classic 是 `眯眼 + 微笑`、calm 是 `闭眼 + 舒展`。前两者一旦关掉贴片，颜色反差最大。

### 复现步骤

打到 100% 触发专属，**在演出期间再点一下屏幕**（或喊一句口令）→ 眼睛立刻回到原色，动作继续播完。
日志里对应一条 `[AppRoot] 交互 #N … → 拒绝`。

> 注意：这不限于"手滑多点一下"。为了把开心值点满，用户的手指本来就在连续点，
> 跨越 100% 之后的那一两下必然落在演出窗口里，所以**正常玩法下几乎每次都会命中**。

### 建议改法（本轮未实施，等确认）

`Refuse()` 只在默认行为（Idle）时改表情，演出期间保持不动：

```csharp
private bool Refuse()
{
    RefusedCount++;
    // 一次性演出（专属 / 共同大笑 / 语音回应）期间，拒绝不应覆盖演出表情。
    if (Current == _defaultBehavior) _presenter.SetExpression(PetExpression.Refuse, 1f);
    return false;
}
```

等价写法：`if (!IsBusy) _presenter.SetExpression(...)`。
**不要**改成"演出结束后补回表情"——那会把表情拖到下一次行为里，反而更乱。

### 验证状态

本轮未能上机复现：15:10 设备断开（`adb devices` 已无设备）。以上结论来自代码路径推导，
复现与验证待重新连接手机后进行。
